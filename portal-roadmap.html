03 How it connects

Three pieces of work, in order.

The front end was written so that connecting a backend is configuration plus one API layer, not a rebuild.

  1. Step 1 · Data

    Export the school's records

    Pupil register, guardians, classes, timetables, assessment marks and the fee ledger. Agree one identifier per pupil (for example GBN-2026-0148) and use it everywhere.

  2. Step 2 · Service

    Build or buy the API

    A small server with four resources — pupils, marks, fees, library — is enough to power all seven modules. Session-based authentication with roles for pupil, guardian and staff.

  3. Step 3 · Wire it up

    Fill in js/config.js

    Set api.baseUrl and the endpoint paths. Swap each portal shell's preview handler for the real sign-in call, then render the data the API returns.

Rules we would keep

  • A guardian sees only the children attached to their account; the server enforces it, not the browser.
  • Marks are visible to a pupil only after the head of department publishes the term.
  • Fee receipts are issued by the server and never editable in the browser.
  • Every sign-in is logged with a timestamp; passwords are hashed, never stored in plain text.
  • Personal data is served over HTTPS only, and the public website keeps no pupil records at all.

What the school needs to provide

A register export, the assessment policy, a fee structure with payment channels, and a named person responsible for accounts. Without those four, a management system becomes a second, contradictory record — the thing this project is designed to avoid.

Ready when you are. The navigation, styling, routing and page structure will not change. Connecting a backend means editing js/config.js and the portal handler in js/site.js.
